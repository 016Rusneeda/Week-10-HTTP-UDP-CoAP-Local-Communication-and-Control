## 4. บันทึกผลการทดลองและคำถามท้ายบท (Lab Report & Questions)
1. นำผลการ Query `/.well-known/core` มาแสดงในรายงาน พร้อมอธิบายรูปแบบ **CoRE Link Format (RFC 6690)** ว่าแสดงข้อมูลทรัพยากรอย่างไร
   
   **ตอบ**
   **ผลการ Query `/.well-known/core`**
   ```</sensor/pot>,</actuator/led>```

  **คำอธิบาย** CoRE Link Format (RFC 6690) เป็นมาตรฐานที่ใช้แสดงรายการทรัพยากร (Resource Directory) ของอุปกรณ์ IoT เพื่อให้ Client รู้ว่ามีเซนเซอร์หรืออุปกรณ์ใดให้ควบคุมบ้าง โดยไม่ต้องรู้ล่วงหน้า รูปแบบจะถูกครอบด้วยเครื่องหมาย < > และคั่นแต่ละ Resource ด้วยเครื่องหมาย ,
   
3. อธิบายความแตกต่างของแพ็กเก็ต CoAP ระหว่าง **CON (Confirmable)** และ **NON (Non-confirmable)** เมื่อทดสอบในเครือข่ายที่มีการรบกวนสัญญาณ

   **ตอบ**
   - **CON (Confirmable)** เป็นแพ็กเก็ตที่ต้องการการตอบรับ (ACK) จากปลายทาง หากเครือข่ายมีสัญญาณรบกวนจนแพ็กเก็ตหาย ระบบ CoAP จะทำการ ส่งซ้ำ (Retransmit) อัตโนมัติ ทำให้เชื่อถือได้ แต่แลกมากับความหน่วงที่เพิ่มขึ้น
   - **NON (Non-confirmable)** เป็นแพ็กเก็ตแบบส่งแล้วส่งเลย (Fire-and-forget) ไม่ต้องการการตอบรับ หากสัญญาณรบกวนมาก แพ็กเก็ตอาจสูญหายได้ทันที แต่ข้อดีคือรวดเร็วและประหยัดพลังงานมาก เหมาะกับการส่งค่าเซนเซอร์ที่อัปเดตบ่อยๆ เช่น ทุกๆ 1 วินาที
   
5. ทำไม CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTP?

   **ตอบ** CoAP จึงเหมาะสมกับโปรโตคอลการสื่อสารบนเครือข่ายเช่น Thread, Zigbee IP หรือ NB-IoT มากกว่า HTTPเนื่องจาก
   1. ใช้ UDP แทน TCP เครือข่ายอย่าง NB-IoT หรือ Thread มีแบนด์วิดท์ต่ำและ Latency สูง การใช้ UDP ทำให้ไม่ต้องเสียเวลาทำ 3-Way Handshake แบบ TCP
   2. ขนาด Header เล็กมาก CoAP ใช้ Binary Header ที่มีขนาดเริ่มต้นเพียง 4 ไบต์ ในขณะที่ HTTP ใช้ Text Header ที่มีขนาดหลายร้อยไบต์ ทำให้ประหยัดดาต้าอินเทอร์เน็ต ซึ่งสำคัญมากสำหรับซิม NB-IoT
   3. มีฟีเจอร์ Observe อุปกรณ์สามารถกดติดตามเซนเซอร์ได้ ทำให้เซิร์ฟเวอร์ส่งข้อมูลมาให้เฉพาะตอนที่มีการเปลี่ยนแปลง โดยไม่ต้องคอยส่ง GET Request ไปถามซ้ำๆ (Polling) แบบ HTTP ซึ่งช่วยประหยัดแบตเตอรี่ของอุปกรณ์ได้มหาศาล
