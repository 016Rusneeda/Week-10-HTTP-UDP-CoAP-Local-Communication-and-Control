#### 1. ตารางบันทึกการคำนวณสัดส่วนประสิทธิภาพข้อมูล (Payload Efficiency)

| รายการประเมิน | HTTP REST (POST) | UDP Datagram | CoAP (PUT) |
| :--- | :---: | :---: | :---: |
| **ชั้นสื่อสาร L4 Transport** | TCP | UDP | UDP |
| **ขนาด L4 Header** | 20–32 ไบต์ | **8 ไบต์** | **8 ไบต์** |
| **ขนาด L7 Application Header** | ~180–250 ไบต์ | **0 ไบต์** | **4 ไบต์** |
| **ขนาดข้อมูลจริง (Payload)** | 14 ไบต์ (`{"state":true}`) | 6 ไบต์ (`LED_ON`) | 1 ไบต์ (`1`) |
| **ขนาดข้อมูลรวม (L4 + L7 + Payload)** | ~214–296 ไบต์ | **14 ไบต์** | **13 ไบต์** |
| **สัดส่วน Payload ต่อข้อมูลรวม (%)** | **~4.7 % - 6.5 %** | **~42.8 %** | **~7.6 %** |
| **ปริมาณข้อมูลเมื่อส่ง 10,000 ครั้ง** | ~2.5 - 3.0 Megabytes | ~140 Kilobytes | ~130 Kilobytes |

> [!TIP] **ประเด็นสังเกตเชิงวิศวกรรม**
> สำหรับอุปกรณ์ IoT ที่ใช้แบตเตอรี่และเชื่อมต่อผ่านซิมเซลลูลาร์ (NB-IoT / 4G) ที่คิดค่าบริการตามปริมาณข้อมูล การส่งคำสั่งด้วย CoAP หรือ UDP จะช่วยประหยัดค่าแบนด์วิดท์และลดระยะเวลาการเปิดใช้วิทยุ (Radio Airtime) ได้มากกว่า HTTP ถึง **15–20 เท่า**

| โปรโตคอล                       | จำนวนรอบที่สำเร็จ | Packet Loss (%) | Min RTT (ms) | Mean RTT (ms) | Max RTT (ms) | Jitter / StdDev (ms) |
| :----------------------------- | :---------------: | :-------------: | :----------: | :-----------: | :----------: | :------------------: |
| **HTTP REST (`/api/led`)**     |  50 / 50   |   0.0 %   | 79.51. ms | 611.25 ms  |  1080.61 ms |     178.98 ms     |
| **UDP Socket (`พอร์ต 3333`)**  |  50 / 50   |   0.0 %   | 5.62 ms | 20.05 ms  | 263.66 ms |     35.14 ms     |
| **CoAP PUT (`/actuator/led`)** |  18 / 50   |   4.0 %   | 17.36 ms | 226.37 ms  | 1091.60. ms |     219.32 ms     |

**วิเคราะห์เชิงเปรียบเทียบจากผลทดสอบจริง**
- **ความเร็ว (Latency)** UDP ทำเวลาได้ดีที่สุดอย่างชัดเจน (Mean RTT เพียง 20.05 ms) เนื่องจากไม่มี Overhead ของ Application Layer และไม่ต้องรอทำ TCP Handshake รองลงมาคือ CoAP (226.37 ms) ในขณะที่ HTTP ช้าที่สุด (611.25 ms) ซึ่งสอดคล้องกับทฤษฎีในใบงานอย่างสมบูรณ์

- **ความเสถียร (Reliability & Jitter)**  HTTP อาศัย TCP จึงไม่พบ Packet Loss เลย (0.0%) แต่แลกมากับความแปรปรวน (Jitter) และเวลาเฉลี่ยที่สูงมาก ส่วน UDP และ CoAP แม้จะมีความเร็วสูงกว่า แต่ก็มีโอกาสเกิด Packet Loss ได้เมื่อเครือข่าย Wi-Fi มีความหนาแน่นหรือถูกรบกวน

#### 3 การตรวจสอบหน่วยความจำบน ESP32 (RAM Footprint)

ตรวจสอบการใช้ทรัพยากรแรมบนบอร์ด ESP32 โดยสังเกตค่า `free_heap` จาก Log Monitor (`idf.py monitor`) หรือจาก HTTP JSON Response (`/api/status`)

| สถานะการทำงานของ ESP32                                 | หน่วยความจำแรมคงเหลือ (Free Heap) | ปริมาณแรมที่ใช้ไปโดยประมาณ |
| :----------------------------------------------------- | :-------------------------------: | :------------------------: |
| **Baseline หลังต่อ Wi-Fi สำเร็จ** (ก่อนรันเซิร์ฟเวอร์) |           ~ 240–260 KB            |       อ้างอิง (0 KB)       |
| **HTTP REST Server (`esp_http_server`)**               |           ~ 210–225 KB            |         ~ 25–40 KB         |
| **UDP Socket Server (LwIP Raw Socket)**                |           ~ 235–250 KB            |       **~ 5–10 KB**        |
| **CoAP Server (`espressif/coap` / `libcoap`)**         |           ~ 190–215 KB            |         ~ 35–50 KB         |

> [!NOTE] **วิเคราะห์เชิงสถาปัตยกรรม:**
> * **UDP Socket** ใช้แรมน้อยที่สุดเนื่องจากเป็นเพียง Socket FD ธรรมดาบน LwIP ไม่ต้องมี State Machine หรือ Context Complex
> * **HTTP Server** ใช้แรมปานกลางสำหรับจัดสรร Connection Slots และ Parsing Buffer
> * **CoAP Server (libcoap)** มีขนาด Task Stack Size (8 KB) และหน่วยความจำสำหรับจัดการ Resource Tree, PDU Session State, และ Observer List

#### 4. วิเคราะห์ผลและสรุปบทเรียนเชิงวิศวกรรม (Engineering Synthesis)

ให้นักศึกษาตอบคำถามเชิงวิเคราะห์ต่อไปนี้ลงในรายงานการทดลอง

### 1. เปรียบเทียบจุดเด่นและจุดด้อย (Pros & Cons Matrix)
จงสรุปข้อดีและข้อจำกัดของ **HTTP, UDP, และ CoAP** จากผลการทดลองจริง 
* **HTTP** จุดเด่น มีความน่าเชื่อถือสูงสุด (Packet Loss 0%) เนื่องจากทำงานบนสแต็ก TCP มีโครงสร้างข้อมูลแบบ JSON ที่อ่านง่ายและยืดหยุ่น และสามารถเรียกใช้งานผ่านเว็บบราวเซอร์มาตรฐานได้ทันทีโดยไม่ต้องติดตั้งไลบรารีเพิ่ม

  จุดด้อย สร้างภาระส่วนหัว (Header Overhead) สูงมาก ส่งผลให้ความหน่วงเวลาตอบสนองเฉลี่ย (Mean RTT) ช้าที่สุดในการทดสอบ (~611 ms) และมีสัดส่วนประสิทธิภาพข้อมูล (Payload Efficiency) ต่ำที่สุดเพียง ~5%
* **UDP** จุดเด่น มีความรวดเร็วสูงสุด (Mean RTT ต่ำเพียง ~20 ms) เนื่องจากไม่มี Overhead จาก Application Layer และไม่ต้องเสียเวลาสร้างการเชื่อมต่อแบบ Handshake อีกทั้งยังใช้ทรัพยากรหน่วยความจำของไมโครคอนโทรลเลอร์น้อยที่สุด

  จุดด้อย ขาดความน่าเชื่อถือแบบ End-to-End หากเกิดความหนาแน่นบนเครือข่าย แพ็กเก็ตอาจสูญหายได้ทันทีโดยไม่มีการส่งซ้ำ รวมถึงข้อความมักจะถูกบล็อกได้ง่ายจากระบบ Firewall ขององค์กร
* **CoAP** จุดเด่น ผสมผสานสถาปัตยกรรมที่ใช้งานง่ายแบบ HTTP (RESTful) เข้ากับความเบาของ UDP ช่วยประหยัดแบนด์วิดท์ได้มากกว่า HTTP มาก (Overhead เพียง 4 ไบต์) เหมาะกับการส่งข้อมูลบนเครือข่ายขนาดเล็ก

  จุดด้อย ในสภาวะที่คลื่น Wi-Fi ถูกรบกวน อาจทำให้เกิดความแปรปรวนของเวลา สูงมาก สูงสุดทะลุ 1,000 ms ในการทดสอบ และจำเป็นต้องติดตั้งไลบรารีเฉพาะฝั่ง Client จึงจะสามารถสื่อสารได้ 

### 2. กรณีศึกษาการตัดสินใจเลือกใช้โปรโตคอล (Engineering Case Studies)
หากท่านเป็นหัวหน้าวิศวกรออกแบบระบบ IoT จงเลือกโปรโตคอลที่เหมาะสมที่สุดสำหรับแต่ละกรณีศึกษาต่อไปนี้ พร้อมให้เหตุผลทางวิศวกรรมสนับสนุน

* **กรณีศึกษาที่ 1** *ระบบเซนเซอร์วัดความชื้นในดินและวาล์วน้ำเพื่อการเกษตรอัจฉริยะ ทำงานด้วยแบตเตอรี่โซลาร์เซลล์ขนาดเล็ก ติดตั้งกลางแจ้งห่างไกล*
  * **โปรโตคอลที่เลือก** CoAP
  * **เหตุผลทางวิศวกรรม** อุปกรณ์ที่ใช้พลังงานแสงอาทิตย์และทำงานระยะไกลต้องการการใช้แบนด์วิดท์ที่ต่ำที่สุดเพื่อประหยัดแบตเตอรี่และค่าส่งข้อมูล (เช่น ผ่าน NB-IoT) โครงสร้าง Overhead ที่เล็กของ CoAP ตอบโจทย์นี้ และยังสามารถใช้คำสั่งแบบ Confirmable (CON) เพื่อรับประกันว่าคำสั่งเปิด-ปิดวาล์วน้ำถึงปลายทางได้

* **กรณีศึกษาที่ 2** *เว็บแดชบอร์ดสำหรับฝ่ายซ่อมบำรุงในโรงงาน เพื่อเปิดดูสถานะและตั้งค่าพารามิเตอร์ของอุปกรณ์ผ่านเว็บบราวเซอร์บนแท็บเล็ต/สมาร์ตโฟน*
  * **โปรโตคอลที่เลือก** HTTP REST
  * **เหตุผลทางวิศวกรรม** แท็บเล็ตและสมาร์ตโฟนรองรับโปรโตคอล HTTP ผ่านเว็บบราวเซอร์ได้แบบ Native ช่วยลดความซับซ้อนในการพัฒนาแอปพลิเคชัน ความหน่วงระดับหลายร้อยมิลลิวินาที (Latency) อยู่ในเกณฑ์ที่ผู้ใช้งานยอมรับได้สำหรับการกดดูหน้าจอสถานะทั่วไป และโปรโตคอลสามารถผ่าน Firewall ของโรงงานได้สะดวก

* **กรณีศึกษาที่ 3** *ระบบควบคุมแขนกลอุตสาหกรรมความเร็วสูง ที่ต้องการส่งพิกัดตำแหน่งแกนหมุน (X, Y, Z) ด้วยความถี่ 100 ครั้งต่อวินาที (100 Hz) ภายในเครือข่าย LAN ปิด (intranet)*
  * **โปรโตคอลที่เลือก** UDP
  * **เหตุผลทางวิศวกรรม** อัตราการอัปเดต 100 ครั้งต่อวินาที ต้องการค่า RTT ที่ต่ำกว่า 10 ms ซึ่ง UDP เป็นโปรโตคอลเดียวที่ทำความเร็วระดับนี้ได้ การส่งข้อมูลบน LAN ปิดช่วยลดปัญหาความไม่เสถียร และหากแพ็กเก็ตพิกัดตำแหน่งบางตัวสูญหาย ระบบก็สามารถนำแพ็กเก็ตใหม่ที่ถูกส่งตามมาในอีก 10 มิลลิวินาทีถัดไปมาประมวลผลแทนได้ทันทีโดยไม่ต้องรอส่งซ้ำให้ระบบชะงัก
